## ① 一般向け（ノンプログラマー向け）

**Ad Studio Light とは**

Meta広告（Facebook・Instagram広告）の「成果分析」と「バナー作成」を1つにまとめた、ローカル実行型のWebツールです。ブラウザで開くだけで使えます。

**何ができるか**

**1. 広告の成績が自動で集まる**
これまで広告マネージャの数字をスプレッドシートに何度もコピペして集計していた作業が不要になります。ツールが毎朝自動でMetaから最新の実績を取り込みます。

**2. 「勝っている広告」がひと目でわかる**
同じクリエイティブを何度も入稿していても自動で1つにまとめて集計し、報酬単価と獲得単価（CPA）から「★★★優秀／★★良好／★継続／要改善／損切り」を自動判定。優先順位表として一覧できます。「どの広告を伸ばし、どれを止めるべきか」の判断材料が毎日そろいます。判定基準（報酬単価など）はクライアントごとに変えられます。

**3. 勝ちパターンから次のバナーをAIが作る**
成果の良かったクリエイティブをAIが分析し、その勝ち要素を活かした新しいバナー案を生成します。「分析→制作→配信→また分析」のサイクルを1つのツールの中で回せます。

**4. 広告アカウントは管理画面で選んで接続**
自社のビジネスマネージャで見える広告アカウント一覧から、分析したいアカウントを検索して登録するだけ。プログラム修正は不要です。

**今後の予定**
性別・年齢・配置（どの面に出たか）ごとの勝ちパターン分析、さらに将来は「勝ちクリエイティブの入稿作業」まで自動化する計画です（入稿は必ず人の承認を挟みます）。

## ② システム担当者向け

**Ad Studio Light — 技術概要**

**概要**: Meta広告のレポーティング・勝ちクリエイティブ分析・AIバナー生成を統合したNext.js製の社内Webアプリ。Meta Marketing API（Graph API v25）から実績を自動同期し、クリエイティブ単位の評価ランキングを生成する。

**スタック**
- フロント/API: Next.js 15（App Router・Route Handlers）+ React + Tailwind
- DB: Postgres（ローカル PostgreSQL 16）。`DATABASE_URL` 未設定時はJSONファイル保存に自動フォールバックする2層ストア構成
- ホスティング: ローカル完結（サーバーには置かない）
- 画像生成: GPT Image 2（PoYo経由=既定 / OpenAI直）、テキスト系LLMは Gemini/OpenAI 自動切替
- リポジトリ: GitHub（ReplusAsiaOrg/design-ad-studio-light-oss）

**データパイプライン**
- **同期**: システムユーザートークン（ads_read）で ①全期間スナップショット（ad単位）②日次ファクト `fact_ad_daily`（`time_increment=1`、広告×日粒度）を取得・upsert。CVはアトリビューション期間内に遡って増えるため、定期実行は直近7日を毎回再取得
- **スケジュール**: ローカル運用のため手動同期が基本（`/api/meta/sync`。自動化する場合はlaunchd/cron等から `CRON_SECRET` のBearer認証で叩ける）
- **主要テーブル**: `accounts`（対象アカウント登録簿）/ `account_settings`（クライアント別評価閾値・jsonb）/ `snapshots` / `fact_ad_daily` / `dim_ad` / `gene_caches`（AIクリエイティブ分析キャッシュ）/ `sync_runs`（実行履歴）

**評価エンジン（scoring.ts）**
- 従来運用のExcel/スプレッドシート（汎用クリエイティブ集計シートv5）の判定ロジックを移植：広告名の名寄せ（日付接頭辞除去）→ 統合名単位で集計 → 報酬単価×ROAS基準から逆算したCPA上限でランクA〜E、消化金額ランクA〜D、総合評価を算出
- 評価はDBに保存せず表示時に計算（閾値変更が全期間に即反映）。閾値は `account_settings` でアカウント別上書き
- **移植の正しさはシート実データで回帰テスト化済み**：入力386行→期待値246行の全件一致を `npm run verify:scoring` で検証
- 制約: リーチは日次値を期間合算できないため、期間指定レポートではリーチ系指標を出さない（全期間はスナップショットから提供）

**異常検知（anomaly.ts・2026-08-03追加）**
- 広告レポート上部に、直近の完了日を過去7日中央値と比較したアラートを表示（消化急増/急減・配信停止疑い・CVゼロ消化・CPA急騰・CTR急落）
- 閾値は絶対額でなく評価設定の★継続ラインCPA（keepLimit）を単位に自動スケール。ベースライン3日未満は判定しない
- Meta APIから直近15日の日次データをオンデマンド取得するためDB不要（`/api/meta/anomalies`）。CV系はアトリビューション計測遅れの注記つき

**学習ループ（generation-history.ts・2026-08-03追加）**
- 生成した全バナーを履歴保存（最終プロンプト・エンジン・パラメータ＋画像実体は `data/generated/images/`。レコードはDBの `generation_history` またはJSONフォールバック）
- 「生成履歴」タブで採用/不採用を記録。採用時は素材名から入稿名（`YYYYMMDD_素材名`）を発行し、その名前で入稿すると既存の名寄せ機構で勝敗が自動追跡できる（「成果を更新」ボタン）
- 追跡した勝敗（★評価・CPA・消化）は「勝ち分析再現」の生成プロンプトに自動注入され、勝った切り口の再現・負けた切り口の回避を学習する

**セキュリティ/運用**
- 全ページ・API に Basic認証（middleware）。CSRF対策としてcross-origin POST遮断
- 秘密情報は `.env.local`＋1Password管理、コード直書きなし
- アカウントIDは `act_\d+` バリデーション（パス・SQLに到達する値のため）

**ロードマップ**
- Phase 1c: 性年齢・配置ブレークダウンの日次同期 → クリエイティブ×セグメントの勝ち抽出 → 入稿用名称生成（※配置×CVのAPI併用可否はトークン受領後に要実測。不可なら Ad Report Run で代替）
- Phase 2: 広告入稿（`ads_management` トークン再発行が必要・人間の承認ステップ必須）、勝ちナレッジの横断DB化
